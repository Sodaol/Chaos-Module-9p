# 2.2-alpha.4 应用隐藏与排序修复

## 2.2-alpha.6 结构修正

2.2-alpha.4/5 曾把排序链的节点数据长度错误地按 C 对齐设为 132，导致
实机隐藏操作在校验阶段被拒绝。原先测试同样用 132 初始化排序链，未发现此错。
新版从固件 reset 的 RW 初始化镜像核对：ROM `0x2c7d1114` 复制至
RAM `0x20096648`，排序头 `0x200a4034` 对应 ROM `0x2c7deb00`，
首字为 **129（0x81）**。包名占 128 bytes，flags 位于 +0x80，
前后链接实际位于 **+0x81/+0x85**，不能假设按四字节对齐。

Rust 校验改用逐字节 volatile 读取未对齐的链接。测试直接从实际 AP 的 RW
初始化镜像取得桌面/排序链头，不再自行填写一个与实现共享的偏移值。
在三个装载地址用旧 alpha.5 镜像均重现隐藏失败；新版以同样的真实结构验证
显隐和排序恢复，并拒绝错误的 132-byte 链头。安装器也新增两个原始链头的
固件指纹校验。操作失败会分别提示桌面链、排序链、文件打开/写入/关闭/提交，
以及回滚恢复失败，避免全部显示同一个「操作失败」。

固件：N67 中国版 3.1.190。AP SHA-256：
`3e264bc267431ec71843cc7c2e4acd928b9280ea39ee1cd888636adcebabf82f`。

## 原因与修复

- `app_launcher_del`（0x0C2A47EC）用于删除应用：除了删除桌面节点，也在
  0x0C2A481E..0x0C2A4836 中从 0x200A4034 的排序链移除并释放包名记录。
  因此旧版隐藏后再显示，会失去原位置。
- 新版只执行该函数的图示清理、桌面节点解除链接与释放步骤，保留排序链。
  排序记录 +0x80 的 bit 1 同步清除，表示该项当前不在桌面；其他位保留。
  显示时调用原生 add，其 `launcher_page_move_icon_before`（0x0C2A3334）
  会跳过隐藏项，依保留的排序记录找回位置。不会先删除已显示的项目。
- 系统应用范围采用该固件 `load_apps` 的 ID 分界（0x0C2A490A..0x0C2A4918，
  0..0x51），并核对 ROM 内应用描述符。单项、批量、取消排除、旧隐藏策略
  均不能绕过保护。列表中 `[S]` 表示受保护的系统应用，隐藏的系统项可恢复显示。
- 旧版策略隐藏的系统应用在模块加载后自动恢复，并清除策略的隐藏位。
  桌面/排序链尚未就绪或保存失败时延后重试，不直接丢弃该维护项。
- 原生注册表、桌面链和排序链在操作前校验；新增相关固件入口的安装指纹。

## 验证

`tools/test_app_manager.py` 在三个装载地址执行实际 ARM 模块与 3.1.190
原生 add/delete/sort/链表指令。测试首先证明旧原生 delete 确实删除排序记录，
再检查新版多项隐藏、交错显示、批量、排除项、保存失败回滚、分配失败、
旧系统策略恢复、启动器延迟就绪、链表损坏拒绝和策略校验。
分配器、字符串比较、存储和 LVGL 为测试替身；不等同于实机测试。

已被旧版删除的排序纪录无法推回原位置，需要手动排列一次。
本次不会尝试恢复不存在的历史数据。原生系统/手机端自行重新排序和卸载行为
仍由原固件处理。

## 构建输入

可从完整 OTA 提取 AP 与原固件字体，不需要重新下载固件：

```powershell
python tools/extract_n67_firmware.py <完整OTA.bin> <输出目录>
$env:CHAOS_FW='<输出目录>/vela_ap.bin'
$env:CHAOS_FONT='<输出目录>/MiSans-Regular.ttf'
python tools/build_n67.py
python tools/verify_port.py
```

其他工具链依赖见 README-9Pro.md。不随本源码包重新分发原始 OTA 或提取的 AP/字体。
